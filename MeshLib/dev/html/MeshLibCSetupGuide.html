Setting Up MeshLib for C Development

Note
Two versions of the C API currently coexist:
- v2 (the recommended default) — the library is called MeshLibC2, and the headers are in the MRC* directories.
- v1 (deprecated) — the library is called MRMeshC, and the headers are in the MRMeshC directory. This version only exposes a small part of MeshLib. The support for v1 will be dropped by the end of 2025.
Note
Currently, the only supported way of using the C API is via the binary releases of MeshLib.
Starting with the next release, you will be able to compile the C bindings directly from the source code.

When the installation is done, confirm the result with Verify the installation — a short program, with the output to expect.

Installing binary releases of MeshLib

The installation process is same as for C++, and is also explained below.

The release archives include the C headers (in the directory called MRCMesh and several other MRC... directories), and a compiled library named MeshLibC2 (MeshLibC2.dll on Windows, libMeshLibC2.so on Linux, etc). This library links against our C++ libraries (MRMesh and others) and provides C wrappers for them.

Windows

Note
MeshLib for Windows is distributed for x64 only: set the platform of your project to x64. A 32-bit (Win32) build of C code compiles, but fails at link with LNK2019: unresolved external symbol __imp__MR_... for every MeshLib function. That means the platform is wrong, not that a library is missing: 32-bit name decoration (__imp__NAME instead of __imp_NAME) matches nothing in the x64 import libraries. Visual Studio 2019 still defaults new C++ console projects to Win32. On Windows on Arm, use the x64 toolchain: no native Arm64 Windows build is published.

Every release publishes one Windows distributive per Visual Studio toolset, plus one for Debug builds that keep MSVC's iterator debugging on. The C++ guide's archive table names all four and says which one to take, including the binary-compatibility rule that lets an older toolset's archive serve a newer Visual Studio. It applies to C unchanged, except for its _ITERATOR_DEBUG_LEVEL column: a pure-C consumer needs no _ITERATOR_DEBUG_LEVEL define, whichever archive it picks, because C code passes no standard containers across the DLL boundary, so the mismatch that define guards against cannot arise. A project that also compiles C++ translation units against MeshLib's C++ headers does need it, at the value in that column.

  1. Download and Extract the Built Version
    • Visit the MeshLib GitHub Releases.
    • Download the archive for your Visual Studio toolset from the C++ guide's table.
    • Extract it to a directory, e.g., C:\meshlib-built\.
      Directory Structure After Extraction
      install/
      ├── include/ # Header files
      ├── lib/ # Static and shared libraries
      ├── app/ # Executables
      example_plugin/ # example solution for creating MeshLib/MeshInspector plugins
  2. Configure and integrate with Visual Studio
    • Solution Platform:
      Set: x64
    • C/C++ → General → Additional Include Directories:
      Add: C:\meshlib-built\install\include
    • C/C++ → All Options → Additional Options:
      Add: /bigobj /utf-8
    • Linker → Input → Additional Dependencies:
      Add: C:\meshlib-built\install\lib\$(Configuration)\*.lib
    • Copy DLLs:
      Copy all .dll files from: C:\meshlib-built\install\app\$(Configuration) to your project’s output directory: $(TargetDir)
      xcopy C:\meshlib-built\install\app\$(Configuration)\*.dll $(TargetDir)

Linux

  1. Download the Package for Your Distribution and CPU
    Open the MeshLib GitHub Releases page: the release description links a .deb for every supported Ubuntu release and architecture. Take the one matching lsb_release -rs and uname -m.
    On any other distribution use the portable Linux vcpkg build instead. It bundles its own dependencies and is not installed system-wide: unpack it and use the resulting directory as the MeshLib installation prefix, then skip to step 3.
    mkdir path_to_install && tar -xf <downloaded>.tar.xz -C path_to_install
  2. Install the Package
    apt refuses a package built for another CPU, but nothing tells the Ubuntu releases apart: both declare the same dependencies and the preinst carries no release check, so installing the Ubuntu 22 build on Ubuntu 24 succeeds silently. Check the release in the file name first.
    sudo apt install ./<downloaded>.deb
  3. Integrate Using CMake
    Add the following to your CMakeLists.txt:
    target_include_directories(your_project_name PUBLIC ${MESHLIB_INCLUDE_DIR})
    target_link_libraries(your_project_name PUBLIC MeshLib::MeshLibC2)

macOS

  1. Download the Installer
    Open the MeshLib GitHub Releases page: the release description links one .pkg installer for macOS Arm (Apple silicon) and one for macOS x64 (Intel). Take the one matching uname -m (arm64 or x86_64).
  2. Install
    • Double-click the downloaded .pkg and follow the installer. The release asset is the installer itself, so there is nothing to unpack first.
    • The framework is installed into /Library/Frameworks/MeshLib.framework, or into ~/Library/Frameworks/MeshLib.framework if you choose to install for the current user only.
    • Install Dependencies via Homebrew
      The .pkg does not pull in the Homebrew formulae MeshLib links against, so install them yourself. Skip this step if your project only uses the C interface. This needs Homebrew — install it first if you do not have it. Open Terminal and run the following command:
      xargs brew install < /Library/Frameworks/MeshLib.framework/Versions/Current/requirements/macos.txt
    • If you installed for the current user only, prefix the path with ~: ~/Library/Frameworks/MeshLib.framework/Versions/Current/requirements/macos.txt.
  3. Integrate Using CMake
    Add the following to your CMakeLists.txt:
    target_include_directories(your_project_name PUBLIC ${MESHLIB_INCLUDE_DIR})
    target_link_libraries(your_project_name PUBLIC MeshLib::MeshLibC2)

Verify the installation

The installer or archive completing is not the same as a working setup: the headers, the import library and the runtime library are three separate things, and any one of them can be wrong while the other two look fine. This program covers the whole chain — compile against the headers, link against MeshLibC2, load it at startup, run a real geometry call, write a file. It needs no input data.

#include <MRCMesh/MRCube.h>
#include <MRCMesh/MRMesh.h>
#include <MRCMesh/MRMeshSave.h>
#include <MRCMesh/MRMeshTopology.h>
#include <MRCMesh/MRVector3.h>
#include <MRCMisc/expected_void_std_string.h>
#include <MRCMisc/std_string.h>
#include <stdio.h>
#include <stdlib.h>
int main( void )
{
int rc = EXIT_FAILURE;
// Build a cube in memory: no input file needed.
const MR_Vector3f size = MR_Vector3f_diagonal( 1.f );
const MR_Vector3f base = MR_Vector3f_diagonal( -0.5f );
MR_Mesh* cube = MR_makeCube( &size, &base );
const MR_MeshTopology* topology = MR_Mesh_Get_topology( cube );
printf( "%d verts, %d faces\n",
MR_MeshTopology_numValidVerts( topology ),
MR_MeshTopology_numValidFaces( topology ) );
// Save it, to exercise the file-format code too.
MR_expected_void_std_string* saveEx = MR_MeshSave_toAnySupportedFormat_3( cube, "cube.stl", NULL, NULL );
const MR_std_string* saveErr = MR_expected_void_std_string_error( saveEx );
if ( saveErr )
fprintf( stderr, "Failed to save mesh: %s\n", MR_std_string_data( saveErr ) );
else
rc = EXIT_SUCCESS;
MR_expected_void_std_string_Destroy( saveEx );
MR_Mesh_Destroy( cube );
return rc;
}

Build and run it on Windows

Build it as the console project configured in Windows above, then run it from the project's output directory.

Build and run it on Linux and macOS

Save the program as verify.c next to this CMakeLists.txt:

cmake_minimum_required(VERSION 3.18)
project(verify C)
find_package(MeshLib CONFIG REQUIRED)
add_executable(verify verify.c)
target_include_directories(verify PRIVATE ${MESHLIB_INCLUDE_DIR})
target_link_libraries(verify PRIVATE MeshLib::MeshLibC2)
Note
MeshLib::MeshLibC2 carries the library but not the header path, so the target_include_directories line is required — without it the build stops at fatal error: MRCMesh/MRCube.h: No such file or directory. Pure C needs nothing else; C++ consumers additionally need ${MESHLIB_THIRDPARTY_INCLUDE_DIR}, as in Integrate Using CMake.
cmake -S . -B build && cmake --build build && ./build/verify

Expected output

8 verts, 12 faces

Exit code 0, and a 684-byte cube.stl next to the binary — a cube is 12 triangles, and binary STL is a fixed 84 + 12 * 50 bytes, so the size is the same everywhere. If you see that line and that file, the installation is working. Anything else — a compiler error about a missing header, a linker error, a loader error at startup, no output — means it is not.

Note
On macOS, v3.1.3.429 and earlier fail at launch with dyld: Library not loaded: @rpath/libMeshLibC2.dylib even though the program compiles and links: the framework's C library was not on the runtime search path. The fix landed after that release, so if you are on it, run the program as
DYLD_LIBRARY_PATH=/Library/Frameworks/MeshLib.framework/Versions/Current/lib ./build/verify

Try MeshLib with C Examples

MeshLib provides a collection of C code samples to help you get started quickly with common mesh processing tasks.

Note that most of them read a mesh from the working directory rather than building one — the Load and Save Meshes sample, for instance, defaults to a file named mesh.stl next to the binary, and exits with an error without it. Its C version also takes the input path as an argument, so ./MeshLoadSave path/to/your.stl works on any mesh you already have. Use Verify the installation above to check the installation itself.
